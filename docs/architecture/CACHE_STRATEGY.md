## 1. Архітектурне обґрунтування вибору механізму збереження

Згідно з вимогою Завдання A3.3 та [ADR-012](file:///C:/Users/cocro/Wather/docs/governance/DECISIONS.md):
- **Оцінка Room:** Підключення реляційної SQLite Room бази вимагає додаткових бібліотек (`androidx.room:room-runtime`, `androidx.room:room-ktx`), KSP анотаційного процесора, збільшує розмір фінального APK на ~1.5–2.0 МБ і створює ризик аварійних завершень (Fatal Crashes) при зміні полів без написання складних міграцій (`Migration(1, 2)`). Оскільки метеорологічні дані є документоорієнтованими агрегатами (`FullWeatherForecast`) без складних багатотабличних реляцій, Room є **надлишковим ускладненням для MVP**.
- **Вибір на користь оптимізованого документно-файлового кешу (`WeatherLocalCache`):**
  - Миттєвий холодний старт (< 10 мс на зчитування).
  - Нуль додаткових залежностей ($0 бюджет, 0 байт збільшення APK).
  - Нативне зчитування з Glance AppWidget без підняття Room драйвера.
  - Повна стійкість до пошкоджень: перехоплення будь-яких помилок десеріалізації з поверненням безпечного fallback без крашу додатку.

## 2. Ключові вимоги та архітектура кешу

| Вимога | Поточний стан (до Phase 2) | Архітектурне покращення в Phase 2 |
|---|---|---|
| **Глибина збереження годин** | Лише 6 годин (`take(6)`) | **Повні 24 години** погодинного прогнозу від поточної години |
| **Глибина збереження днів** | Лише 5 днів (`take(5)`) | **Повні 14–16 днів** денного прогнозу |
| **Кілька міст (Multi-city)** | Тільки 1 активна локація | **Збереження прогнозу для кожного міста** за ключем `cache_${lat}_${lon}` |
| **Ознака застарілості** | Поле `isStale` | Розрахунок `isStale = true`, якщо минуло > TTL хвилин або сталася мережева помилка |
| **Час оновлення** | Фіксується `updatedAt` | Збереження точного `LocalDateTime` в ISO-8601 |
| **Джерело даних** | Не завжди персистилося | Обов'язкове збереження `WeatherDataSource` (WeatherMetro, Open-Meteo тощо) |
| **Пошкодження кешу** | Просте ігнорування | **Corrupted Cache Recovery:** автоматичне очищення битого JSON та відкат до дефолтної або мок-локації |

## 3. Схема ключів локального сховища (`SharedPreferences`)

```
weather_local_cache.xml
├── loc_id: Long                          # ID активної локації
├── loc_name: String                      # Назва активної локації
├── loc_lat: Float                        # Широта активної локації
├── loc_lon: Float                        # Довгота активної локації
├── loc_tz: String                        # Часовий пояс (Europe/Warsaw)
├── loc_is_gps: Boolean                   # Чи визначено за GPS
├── selected_cities_json: String (JSON)   # Список збережених міст (до 10 міст)
├── forecast_active_json: String (JSON)   # Повний прогноз для активної локації (для Glance віджета)
└── forecast_cache_${lat}_${lon}: String  # Кеш повного прогнозу для конкретного міста
```

## 5. Обробка помилок та відновлення при пошкодженні (Corrupted Cache Recovery)

Якщо файл налаштувань пошкоджено (наприклад, раптове вимкнення живлення пристрою під час запису):
1. Метод `loadCachedForecast()` або `loadActiveLocation()` перехоплює `JSONException` та `DateTimeParseException`.
2. Пошкоджений запис атомарно видаляється через `.remove(key).apply()`.
3. Система повертає безпечний fallback — `DEFAULT_LOCATION` (Пшецлав/Київ) або дані з `MockWeatherRepository`.
4. Застосунок **ніколи не завершується аварійно (0 Crash Policy)** через некоректний дисковий кеш.
