# Критерії готовності (Definition of Done — DoD)

> Цей документ визначає обов'язкові критерії, за яких завдання, зміна або етап вважаються виконаними.
> Порушення DoD (наприклад, позначення «Готово» без доказів) є Червоною лінією №1 Конституції v2.0.

---

## 1. Рівні готовності

| Рівень | Що це | Хто затверджує |
|---|---|---|
| **Code Ready** | Код написано, unit-тести проходять локально, лінт чистий | Автор завдання |
| **Contract Validated** | Інтерфейси між модулями (UI <-> Domain <-> Data) дотримано, mock-дані валідні | Автор та інтегратор (Agent 0) |
| **QA Verified** | Проведено незалежну верифікацію тестів, збірки, дозволів та поведінки | **Лише інший агент (QA) або Власник** (п. 2.1 Конституції: автор не верифікує власну роботу) |
| **Merged to Main** | Зміни влито в основну гілку після `QA Verified` та проходження перевірок | Agent 0 (у межах п. 3.1) |
| **Owner Approved** | Стратегічні рішення, проходження етапних воріт, реліз або зміна дозволів | **Лише Власник** (п. 3.2 Конституції) |

---

## 2. Критерії для кожної картки завдання (Task-level DoD)

Завдання може бути переведене в статус `DONE` тільки якщо:
1. **Відповідність вимогам:** Усі критерії приймання (Acceptance Criteria) з картки завдання реалізовано.
2. **Збірка:** Код компілюється без помилок та критичних попереджень.
3. **Тести:** Написано та успішно виконано автоматичні тести для нової логіки (unit/domain/parser). Жоден наявний тест не поламано і не вимкнено.
4. **Приватність і безпека:**
   - Жодних API-ключів, токенів чи паролів у коді чи історії комітів.
   - Жодних збережень точних координат користувача в локальних логах чи звітах.
   - Відсутність background location (`ACCESS_BACKGROUND_LOCATION` суворо заборонено).
   - Жодних сторонніх трекерів, аналітики чи рекламних SDK.
5. **Документація:** Оновлено коментарі, документацію контрактів (якщо змінювались API/моделі).
6. **Журнал картки:** Додано запис у картку завдання відповідно до п. 5.3 Конституції (зроблено, зупинився на, наступний крок).
7. **Незалежна перевірка:** Отримано підтвердження `QA Verified` від профільного QA-агента або Власника з конкретними фактичними доказами (вивід тестів, скриншоти, diff-аналіз).

---

## 3. Критерії для UI та візуальних компонентів

1. **Доступність (a11y):** Всі інтерактивні елементи мають описові `contentDescription`; контраст тексту відповідає стандартам WCAG AA; розмір клікабельних зон >= 48dp.
2. **Адаптивність та теми:** Підтримка динамічної зміни світлої та темної тем, адаптація до різних розмірів екранів та орієнтацій.
3. **Керування рухом (Motion):** Усі погодні анімації перевіряють стан системного прапорця `reduced-motion` і вимикаються або замінюються на статичні графічні аналоги при його активації.
4. **Стани екранів:** Кожен екран обов'язково обробляє 4 базові стани: `Loading`, `Success` (з даними), `Empty` (порожньо) та `Error / Offline` (з кнопкою повтору та індикацією застарілості даних).

---

## 4. Критерії для віджета (AppWidget / Glance)

1. **Енергоефективність:** Оновлення даних здійснюється за системним розкладом або за явним оновленням з основного застосунку, без постійного фонового опитування.
2. **Відсутність покадрової анімації:** Жодних нескінченних важких циклів анімації у віджеті (відповідно до обмежень Android RemoteViews).
3. **Обробка відсутності мережі:** Віджет показує останній відомий прогноз із позначкою часу або стан потреби оновлення, не падаючи при помилках мережі.

---

## 5. Критерії для етапних воріт (Phase Gates)

Перехід між етапами дорожньої карти вимагає:
1. Завершення всіх обов'язкових завдань етапу.
2. Оновлення всіх файлів пам'яті (`CURRENT_STATE.md`, `TASK_BOARD.md`, `SESSION_LOG.md`, `DECISIONS.md`).
3. Складання підсумкового звіту етапу `docs/reports/PHASE_GATE_<phase>.md`.
4. Отримання `Owner Approved` для дій, які зачіпають п. 3.2 Конституції.
